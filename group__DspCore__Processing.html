Detailed Description

Typed, zero-copy fixed-size sample-block views.

Ownership and processing model

DspCore separates signal memory from signal processing:

Caller-owned input samples ---> SampleBlock<const T> ---> DspCore algorithm
Caller-owned output samples <--- SampleBlock<T> <--- DspCore algorithm

SampleBlock is a small, non-owning view over externally owned contiguous samples. It never allocates, copies, frees, queues, resamples, schedules, timestamps, or routes samples. The caller owns the backing memory and keeps it alive for the duration of the Process call.

DspCore algorithms own no external input or output block. They may own internal algorithm state: FIR owns taps and delay history, while IIR owns numerator, denominator, and delay histories. This makes a JUCE callback or a microcontroller DMA buffer usable without an intermediate copy.

Typed n-to-n blocks

The owner normally constructs the input and output views when it prepares its buffers, then can reuse those views across process calls:

const float audio[] = { 1.0F, 0.0F };
float result[2]{};
const SampleBlock<const float> audioBlock{audio, 2U};
const SampleBlock<float> resultBlock{result, 2U};
Filters::FIR<float> filter;
filter.Configure(taps, tapCount);
filter.Process(audioBlock, resultBlock);

MakeInputBlock(data, size) and MakeOutputBlock(data, size) provide the same views at an integration boundary that only exposes a raw pointer and size, such as an audio callback. Neither form copies the samples.

SampleBlock<const float> makes the input read-only at compile time, while SampleBlock<float> represents writable output. SampleBlock itself may describe any element type; a particular DspCore algorithm can impose a narrower requirement. FIR and IIR require arithmetic SampleType values.

The block extent is its size: there is deliberately no capacity or produced-count distinction in this layer. FIR and IIR are synchronous n-to-n transforms and reject invalid blocks or unequal input/output sizes before touching their state or output. Empty blocks are valid and retain state.

Lifetime and aliasing

A block is a borrowed view, not a container. It must not outlive the caller's memory. A filter may process exactly in place when input and output start at the same address. Partially overlapping, different ranges are not supported.

What processing does not provide

DspCore is not a graph owner, stream clock, sample-rate converter, thread synchronizer, FIFO, MIDI/event transport, or port-routing system. A future stream/runtime library will own those concerns, including heterogeneous audio, MIDI, envelope and event transport. It can adapt its buffers to these typed blocks at the boundary.
