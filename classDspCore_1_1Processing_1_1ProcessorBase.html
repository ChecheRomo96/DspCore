Detailed Description

template<typename Real>
class DspCore::Processing::ProcessorBase< Real >

MIMO base interface for a processor that consumes and produces blocks.

A processor exposes an ordered input/output port layout. The caller supplies one InputBlock for each input port and one OutputBlock for each output port. This describes the processing contract only: it is not a graph, does not connect processors, does not select an audio backend and does not prescribe whether a block represents audio, modulation, measurements or another signal format.

Implementations may support blocks of one value, so sample-wise processing is a valid special case. Every call is synchronous: all input blocks have the same length n and, on success, every output block contains exactly n values. A processor with accumulation, window overlap or intrinsic latency retains that state internally while preserving this n-to-n contract. The caller owns all supplied storage. Implementations must not allocate, resize, free or retain the supplied block storage during Process. FIR and IIR are SISO implementations: each reports one input port and one output port, consuming and producing equally sized signal blocks.

Processes one block for every input and output port.

inputs and outputs must be non-null when their corresponding count is nonzero. inputCount must equal InputPorts and outputCount must equal OutputPorts. Each input must be valid and have the same length n. Each output must have capacity for n values. On a successful return, every output's size equals n. On failure, an implementation may have processed a valid input prefix and reports its valid output extent through size; it documents whether state was committed. Calls with malformed ports, invalid block views or insufficient output capacity or unequal input lengths must be rejected before processing begins. Input and output storage may overlap only when the derived processor explicitly documents support for it.
